Eval Boards

An ontology-grounded analytics agent, built for a fictional skateboard manufacturer.

I built an AI agent that answers business questions using only the metrics a company has actually defined — and I published a scorecard showing how often it's right and how often it correctly refuses to answer.

In the run below, it traced a spike in warranty claims back through production batches to a single bad material lot from one supplier, and proposed quarantining the affected batches for a human to approve.

Eval Boards is an analytics agent that answers questions about a manufacturing business by calling tools generated from a small, explicit ontology — never by writing its own SQL — and it is measured the same way it is built: by how often it gets the right answer, how often it correctly says "I can't answer that," and whether it recovers or fabricates when a tool call fails.

All of the data below is synthetic. "Eval Boards" is not a real company; the batches, suppliers, claims, and orders are generated by a seeded random process for the purpose of this project.

Why delamination_claim_rate is defined this way

Every metric the agent can compute carries a rationale field — prose a VP could be handed directly, explaining the definitional choice, not just the formula. This is the one that mattered most in the flagship trace above: it's the difference between the agent measuring a real problem and measuring an aging artifact.

Definition

Warranty claims with defect_type “delamination” per 100 decks, counted only among decks that have reached 90 days of field maturity (90 days since ship_date as of the metric's as-of date). Decks younger than 90 days are excluded from both the numerator and the denominator.

Rationale

Delamination is a defect that surfaces with use, not at the moment of sale — a deck typically has to be ridden, get wet, and take a few impacts before a sub-par adhesive bond starts to show itself. A metric of raw claims over decks shipped is biased toward whichever batches are oldest, because they have had the most time to accumulate claims, and it is biased against the newest batches, which look artificially safe simply because they have not been skated long enough to start to fail. That makes "raw claims over shipped" actively misleading during exactly the window when catching a bad batch matters most: a newly-discovered material problem would look clean under that definition for months, by which time far more decks have shipped. Matching on maturity — comparing batches only once each has had the same amount of field time — is what makes the batches comparable at all, and it is the difference between "we have a lot problem" and "we have a plausible pattern that might just be an aging artifact."

Architecture

Everything the agent can talk about is declared once, in agent/ontology/eval_boards.yml: nine object types (Deck, ProductionBatch, MaterialLot, Supplier, and so on), the named directional links between them, three actions it may propose, and five metrics — each with a grain, an allowed set of filters, and that rationale field. Nothing else in the codebase is allowed to define a new one.

Why tool schemas are generated, not hand-written

The six Anthropic tool schemas (list_available_metrics, get_metric, compare_periods, get_object, traverse_link, propose_action) are built from the loaded ontology at import time — the enum values for metric names, link names, and filterable fields all come straight out of the YAML. Adding a sixth metric changes what the agent can compute with zero code changes, and there is no path by which the model can reference a metric, link, or field that isn't declared: the SQL compiler (agent/ontology/compiler.py) validates every metric name, filter field, grain dimension, and link name against the ontology before it will build a query, and raises rather than silently falling through to string interpolation of an unchecked name. Nothing in this project ever executes free-form SQL.

A coverage guard runs before the agent loop even starts, deciding — as a separate model call with nothing but the ontology's declared surface area in front of it — whether a question is answerable at all. That's deliberate: the model answering the question has every incentive to be helpful and stretch toward an answer, so the scope check is a hard boundary enforced outside that conversation, not a judgment call left to it.

The closed loop is what makes this an agent rather than a formatter: propose_action never mutates warehouse data — it only ever writes a pending_approval row. A human approves separately (runtime.approve), and an approved quarantine_batch then changes what build_metric_query returns on every subsequent call, with the held-out batches surfaced back to the agent so it can say which ones were excluded and why.
